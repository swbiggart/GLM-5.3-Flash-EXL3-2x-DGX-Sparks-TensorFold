**Two capacities share `TF_GLM_CACHE_GIB`**

For multiple streams, `cuda_engine.zig:358–378` uses `TF_GLM_CACHE_GIB` (fallback `KV_POOL_GIB`, default3 GiB) to cap **surplus active KV pool capacity** after fixed arenas/drafter and the memory reserve. It computes additional pool rows, accounts for scratch growth, then agrees the smallest capacity across ranks (`:380` onward). This is separate from the kept-state budget in `cacheFor`/`cuda_cache_plan.budgetBytes`. `--prompt-cache-gib` overrides only that kept-state budget: **env32 + CLI0 still creates the env32-sized active KV pool while disabling kept states**. The comment at engine line359 saying there is no prompt cache is stale relative to `cuda_native.zig:226–264`; the implementation has both capacities.

Root-provided live evidence (not independently rerun by this read-only task): `TF_GLM_CACHE_GIB=32` yielded **5,619,712 KV rows**; env3 yielded **651,264 rows**. These are observations for the tested startup/memory/profile, not a universal conversion from GiB. Root reports testing env32 + `--prompt-cache-gib 3`; no outcome is asserted here.

To isolate kept-state caching, hold the environment KV capacity setting fixed and compare CLI0 versus CLI3, recording actual agreed pool rows, actual kept-state budget, memory availability/reserve, cache hits and prefix workload. Do not attribute an env3/CLI0 versus env32/CLI3 difference solely to prompt caching: both active capacity and kept-state behavior change. Record served context separately; extra shared KV rows are not proof of a larger per-request context. Even with fixed env, startup memory can cap the pool differently, so compare the effective row count rather than the requested value alone.

**Transport settings and rebuild boundary**

- `TF_GLM_TRANSPORT=nccl|roce|neighbor` is explicit; legacy `TF_GLM_ROCE=0` selects NCCL when transport is unset. Explicit `roce` requires successful setup. `TF_GLM_ROCE_MEMORY=allocated|registered` selects the relay host allocation/registration path; NCCL rejects registered/required RoCE profiles. Neighbor requires TP4, registered memory, explicit pinned FIRST/SECOND and GID3. Profile mismatch fails collectively (`cuda_comm.zig:738–793`; `cuda_neighbor.zig:18–35`).
- **Registered relay cutoff is tunable without rebuilding:** `TF_ROCE_MAX_KB`, default512, controls per-rank slot size/cutoff. Underlying layout accepts positive multiples of4 KiB up to1 GiB; use the bounded512/1024 KiB experiment, not the broad implementation maximum. Invalid numeric text falls back512; invalid layouts fail opening. All ranks must match. `TF_ROCE_WAIT_S`1..3600, default600, is a failure timeout, not a speed setting (`cuda_comm.zig:223–235,404–416`; `zig/src/cuda/roce_proxy.c:148–150`).
- **Relay stage/collect block geometry is not exposed:** one combined GPU gather uses512 threads, size-derived blocks clamped1..16, 16-byte or4-byte copy units. There is no runtime stage/collect env parser; registered memory uses the same path. Changing the cap/formula requires a new binary. Prefetch blocks are distinct, up to64 at512 threads (`zig/src/cuda/roce.zig:48–81,269–298`).
- **Neighbor cutoff requires rebuilding:** `cuda_neighbor.zig:7` fixes512 KiB per rank; two stages allocate max1 MiB and scratch1 MiB. `TF_ROCE_MAX_KB` does not change it. Settings defaults are slots4, stage_blocks16, collect_blocks48, collect_grain4, stage_threads512, collect_threads256. Adapter explicitly sets PDL=false; no `TF_RDMA_*` environment parsing wires the other fields. Changes require source/rebuild/byte-and-graph requalification (`cuda_neighbor.zig:7,27–32`; `neighbor_rdma.zig:20–43,436–438,505–506`).
- Eligible neighbor transfers are disjoint,16-byte aligned and at most cutoff; ineligible calls select NCCL before enqueue. Failures after neighbor selection poison the path, with no mid-transfer fallback. Model FP32 reduction remains outside gather (`cuda_neighbor.zig:75–97`; `cuda_comm.zig:466–502`; `cuda_forward.zig:264–270`).

**Aggregate verify rows and probe03 cutoff qualification**

The16-row native serving window (`cuda_native.zig:123`) is per stream, not the aggregate gather limit. Engine workspace is64 (`cuda_engine.zig:180–182`), and scheduler `batch_rows=min(64, streams*window)` (`cuda_lanes.zig:14,340`). Each row gathers4096 FP32 values,16 KiB per rank (`cuda_forward.zig:268`). Thus32 rows=512 KiB;33=528 KiB;64=1024 KiB. Multi-stream drafted rounds can cross512 KiB, including at parallel4/8; actual row counts need runtime evidence. Raising relay cutoff can therefore affect real verify traffic, not merely synthetic sizes.

Probe03 at inspected HEAD `b733c37688c44772332f99515b26e7fe21f20ff7`, `zig/tests/cuda/glm_transport_probe.zig:52`, eagerly checks sizes through1 MiB. Its captured graph is fixed at16 KiB,512 KiB+16 bytes,32 KiB (`:81`), and `:94` **requires the middle backend to be NCCL**. It does not derive this boundary from relay.slot_bytes. With relay1024 KiB, that middle call becomes RoCE and the probe fails `ProbeRequiresFallbackMiddle` before graph capture. Therefore1024 KiB is configurable without a production rebuild but **cannot receive complete byte/graph qualification from unchanged probe03**. Rebuild/review a probe with an explicit above-active-cutoff fallback and custom graph cases for528 KiB and1 MiB. Existing512 KiB profile tests do not establish custom graph replay at those larger sizes. Neighbor remains compiled512 KiB and requires a production rebuild as well to cover them.

Most such changes require implementation/rebuild here; this inventory does not authorize them.
